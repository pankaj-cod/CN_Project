Part 1: The big picture (everyone)

The 30-second opening (memorise)

"We built a small private cloud on 4 Macs. A user types app.teamX.test. Mac 1 is our DNS server and turns that name into an IP address. The client then connects over HTTPS to Mac 2, which runs nginx. nginx decrypts the request and forwards it to one of two backend servers, Mac 3 (Backend A) or Mac 4 (Backend B), taking turns. That is load balancing.

Phase 1 built this. In Phase 2 we made it resilient: a backup DNS, automatic failover between backends, a firewall so nobody can bypass nginx, a standby nginx we can switch to with DNS, and a step-by-step method to find faults."

Member 1 Mac 1: DNS, Ext A, Ext B (+ main client)

Concepts you must explain

  • DNS = the phonebook of the network: turns a name into an IP. Uses port 53, normally UDP.
  • dnsmasq = the small DNS server program we run. It answers our team names itself and forwards other names (google.com) to the normal network DNS.
  • .test is a reserved top-level domain that never exists on the internet, so no conflicts.
  • A record = name → IPv4 address. Ours: app.teamX.test → 10.7.3.24.
  • TTL (Time To Live) = how many seconds a client may cache (remember) an answer. Ours = 30 s.
  • Resolver / cache: macOS remembers answers (mDNSResponder). dig @server asks the server directly (no cache); curl/browsers use the cached OS answer.
  • Flush = clear the OS cache now: dscacheutil -flushcache + killall -HUP mDNSResponder.

Ext A: Backup DNS

What: a second dnsmasq on Mac 3 with exactly the same records (made from the same template). Clients list both servers: Mac 1 first, Mac 3 second.

Why: if DNS dies, nobody can find the site, even though the site itself is fine.

Demo: stop Mac 1's DNS; the live view shows dns1 down but requests stay 200 (the client falls back to Mac 3). The first lookup after the failure is slower (timeout, then retry on the backup).

Say: "A DNS failure means you can't find the server. An application failure means you find it and connect, but the service behind it is broken (502). Different layers, different symptoms."

Ext B: TTL and a controlled record change

Phase 1 problem: we used address= records, which dnsmasq answers with TTL 0, so nothing was cached. Now we use host-record=name,IP,30.

Demo: change app to Mac 4's IP on both DNS servers. The DNS columns in the live view change immediately, but the CONNECTED column keeps the old IP for up to 30 s, then switches. Then change back and flush: it switches at once.

Say: "Short TTL: changes spread fast, but more DNS queries. Long TTL: fewer queries, but changes are slow. Before a migration, companies lower the TTL a day early. A flush only fixes my Mac; you cannot flush other people's caches. That is why TTL planning matters."

Likely questions for you

What happens if both DNS servers are down?Names can't be resolved: curl says "Could not resolve host". But ping 10.7.3.24 still works; the network is fine, only name lookup fails.
How does the client know to use the backup?We configured two DNS servers (networksetup -setdnsservers). If the first doesn't answer within its timeout, the OS asks the second.
Why must both servers have the same records?Otherwise clients get different answers depending on which server they asked. During a change, update both.
Difference between dig and what curl uses?dig @server asks that server directly, no cache. curl uses the OS resolver, which caches for the TTL.
Why UDP for DNS?Small, single question/answer; no handshake needed, so it's fast. TCP is used for large answers.
What does local=/teamX.test/ do?Our server is authoritative for teamX.test: unknown names get NXDOMAIN locally and are never sent to the internet.
How are non-team names (google.com) resolved?dnsmasq forwards them to the network's normal DNS (server= lines, with no-resolv so the two team servers can't loop).

Member 2 Mac 2: nginx edge, TLS, load balancing, Ext D

Concepts you must explain

  • Reverse proxy: clients talk only to nginx; nginx talks to the backends on their behalf. Clients never see the backend IPs.
  • TLS termination: nginx holds the certificate and private key, decrypts HTTPS, and forwards plain HTTP inside the private network. Client→edge is encrypted; edge→backend is plain.
  • Certificate: proves the server is app.teamX.test (the name is in the SAN field) and enables encryption. Ours is self-signed, so every client Mac added it to its trusted keychain. We never use curl -k (that ignores certificate errors).
  • Load balancing: upstream block with 2 servers, default round robin (A, B, A, B).
  • Port 80 redirects to 443 (HTTP → HTTPS).

Ext D: High-availability failover

Our upstream config:

upstream backend_servers {
    server 10.7.0.215:3001 max_fails=1 fail_timeout=5s;
    server 10.7.3.165:3002 max_fails=1 fail_timeout=5s;
}
proxy_next_upstream       error timeout http_502 http_503 http_504;
proxy_next_upstream_tries 2;
proxy_connect_timeout     2s;
  1. A request goes to A; the connection fails (refused, or no answer in 2 s).
  2. nginx retries the same request on B, so the user still gets 200.
  3. A is marked unavailable for 5 s (fail_timeout); all traffic goes to B.
  4. After 5 s nginx tries A again with a real request; if it answers, round robin resumes.

This is a passive health check (it learns from real requests). Active health checks (regular test requests) exist in nginx Plus / cloud load balancers.

Say: "When A died, the user saw no error: nginx retried on B. Our edge log shows ustatus="502, 200", the failed try on A and the success on B."

502 vs 504 (very likely question)

CodeMeaningTypical cause in our setup
502 Bad Gatewaynginx reached the backend Mac, but the connection was refusedMac is on, node is not running
504 Gateway TimeoutNo answer at all within the timeoutMac is off / asleep, or a firewall drops packets

With both backends down, /edge-health still answers (nginx answers it itself). That proves the edge is alive and only the backends are broken.

Single point of failure (SPOF)

Say: "With a backup DNS and two backends, the remaining single point of failure is this nginx on Mac 2: it is the only IP the name points to. If it dies, everything dies even though both backends are healthy. Fixes: a second edge with a floating virtual IP (keepalived / VRRP), DNS failover with health checks (what Ext E does by hand), or a managed load balancer like AWS ALB across availability zones. Other shared dependencies: the single Wi-Fi/router."

Likely questions for you

Why terminate TLS at the edge?One place holds the certificate; backends stay simple; nginx can read the HTTP request to route and add headers.
Is plain HTTP to the backends safe?Acceptable inside a private network protected by the firewall. In production you could re-encrypt (mTLS) to the backends.
What is SAN?Subject Alternative Name: the list of names the certificate is valid for (app.teamX.test, api.teamX.test).
What headers did you add?X-Edge (which nginx answered: primary/standby), X-Upstream (which backend(s) nginx tried), and backends add X-Backend.
How fast is failover?The failing request is retried immediately; at most a ~2 s connect timeout if the Mac is off. The bad backend is skipped for 5 s.
What does the backend see as the client IP?The edge's IP (10.7.3.24). The real client IP is passed in X-Forwarded-For.

Member 3 Mac 3: Backend A, backup DNS, Ext C (firewall)

Concepts you must explain

  • Backend: a small Node.js (Express) server. Backend A listens on port 3001 on all interfaces (0.0.0.0), answers /api/status with JSON and header X-Backend: A.
  • Port: the IP finds the machine, the port finds the program on it.
  • pf = macOS's built-in packet filter (firewall), configured with pfctl.
  • Anchor: a named sub-section of the pf rules. We put our rules in com.apple/cn-project, so the system file /etc/pf.conf is never edited.
  • Table <edges>: the list of IPs allowed in (Mac 2, and Mac 4 in Ext E).

Ext C: Service isolation

Problem: before the firewall, anyone on the Wi-Fi could connect directly to http://10.7.0.215:3001, bypassing nginx: no HTTPS, no load balancing, backend exposed.

Our rules (firewall/pf-backend.rules.template):

table <edges> persist { 10.7.3.24 }                      # Mac 2 = the edge
pass  in quick on lo0 all no state                        # local traffic always OK
pass  in quick proto tcp from <edges> to any port { 3001 3002 } keep state
block drop in log quick proto tcp from any to any port { 3001 3002 }

Read it top to bottom: "quick" means the first matching rule wins. Edge → allowed. Everyone else to 3001/3002 → silently dropped.

Demo: before: Mac 1 sees both backends OPEN. After apply: Mac 1 sees BLOCKED (but ping still works: the host is reachable, only the port is filtered). Mac 2 still sees OPEN. The website still works through nginx.

Rollback: apply first saves a copy of /etc/pf.conf and a snapshot of the live rules in ~/.cn-project/firewall/. rollback flushes our anchor, releases our pf "enable token" (pf returns to exactly its old on/off state), and compares with the snapshot.

Say: "Only the edge may talk to the backends. This is the same idea as a cloud security group: backends sit in a private subnet and only accept traffic from the load balancer's group. We used drop, not reject: drop sends nothing back, so the client just times out, which hides the service. Reject would send an immediate 'connection refused'."

Likely questions for you

Why does ping still work after the firewall?We only block TCP ports 3001/3002. ICMP (ping) is not blocked. It proves the host is up and only the port is filtered.
"Timed out" vs "connection refused"?Timed out = packets dropped (firewall, or host off). Refused = host answered with a TCP RST: reachable, but nothing listening on that port.
Why the lo0 rule?So local (same-machine) traffic is never blocked by accident.
Why is Mac 4 added in Ext E?The rule matches on source IP. The standby edge has a different IP, so it must be added to <edges>.
Is the backup DNS on the same Mac a risk?Yes, Mac 3 dying takes out Backend A and the backup DNS. But it's a different Mac from the primary DNS, which is what matters for Ext A.
Did you edit /etc/pf.conf?No. The stock file already loads every com.apple/* anchor; we only load rules into our own anchor.

Member 4 Mac 4: Backend B, standby edge, Ext E, Ext F

Concepts you must explain

  • Backend B: same Node.js app as A, on port 3002, header X-Backend: B.
  • Standby edge: a second nginx on Mac 4, made from the same template as Mac 2 (same backends, TLS, timeouts). Only difference: X-Edge: standby.
  • It uses the same certificate and key as Mac 2. A certificate is issued for a name, not an IP, so it is valid on any Mac serving that name.
  • DNS cutover: moving users from one server to another by changing the DNS record.

Ext E: Controlled edge migration

  1. Test the standby before switching, without touching DNS:
    curl -s --resolve app.teamX.test:443:10.7.3.165 https://app.teamX.test/edge-health → {"edge":"standby"}
  2. Allow Mac 4 through the firewall: ./firewall/firewall.sh allow-standby (Mac 3 and Mac 4).
  3. Change the record on both DNS servers: ./dns/dns.sh set app $STANDBY_EDGE_IP.
  4. Watch: the live view's EDGE column goes primary → standby within 30 s (the TTL). Mac 2's access log stops receiving requests. That means the old edge has drained.
  5. Roll back: ./dns/dns.sh set app $EDGE_IP.
Say: "Clients only know the name, never the IP, so we can move the server with a DNS change alone. During the TTL window both edges must keep running: if we shut the old one first, clients with a cached answer would break for up to 30 s. DNS moves new lookups, not existing connections."

Ext F: Troubleshooting method

Always go in the order the packets travel. The first layer that fails is the cause; everything above it is just a side effect.

#LayerQuestionCommandTypical faults
0Client configWhich DNS server does this Mac use?scutil --dns | headDNS changed to a wrong server
1IPCan I reach the machine?ping 10.7.3.24Wi-Fi off, Mac asleep, IP changed
2DNSDoes the name give the right IP?dig app.teamX.testdnsmasq stopped, wrong record, stale cache
3TCPIs the port open?nc -vz 10.7.3.24 443nginx stopped (refused), firewall (timeout)
4TLSIs the certificate trusted and valid for the name?openssl s_client -connect 10.7.3.24:443Cert not trusted, wrong name, expired
5HTTP / appWhat status code? Which backend?curl -si https://app.teamX.test/api/status502 backends down, only one backend answers

./scripts/diagnose.sh runs all of these in order and prints a Verdict. Read the verdict out loud, then fix that layer (see Part 4 fix table).

Say: "We don't guess. We check DNS, then IP, then the port, then TLS, then HTTP. The first one that fails is the cause. For example, if ping works but DNS doesn't, it's not the network. It's name resolution."

Likely questions for you

Why not just switch the IP instantly?Clients cached the old answer for up to the TTL. You can't flush other people's caches; you wait for the TTL.
How do real companies avoid this delay?Lower the TTL before migrating, or use a floating IP / anycast / managed load balancer so the IP never changes.
Why copy the private key, and is that safe?The standby needs it to prove it is app.teamX.test. Copy it only over a trusted channel (AirDrop), never into git; it's a secret.
What does --resolve do?Pins the name to an IP for one curl request. TLS still checks the name, so it's a real test without changing DNS.
Ping works, website doesn't. Where do you look?IP layer is fine, so check DNS (dig), then the port (nc), then TLS, then HTTP status.

Part 3: Common questions (everyone must know)

QuestionAnswer
Explain the whole flow.Name → DNS (Mac 1) → IP 10.7.3.24 → TCP handshake on 443 → TLS handshake (certificate) → encrypted HTTP → nginx picks A or B → plain HTTP to the backend → response back the same way.
What is a private network?Addresses like 10.x.x.x are private (RFC 1918). They work only inside the local network, not on the internet.
TCP vs UDP?TCP: connection, handshake, reliable, ordered (HTTP/HTTPS). UDP: no connection, fast, no guarantee (DNS).
TCP 3-way handshake?SYN → SYN-ACK → ACK. Then data can flow.
What does TLS give you?Encryption (privacy), integrity (no tampering), authentication (the certificate proves the server's identity).
HTTP vs HTTPS?HTTPS = HTTP inside TLS, port 443. HTTP is plain text, port 80.
What is load balancing?Spreading requests across several servers for capacity and resilience. Ours: round robin with retry.
What is high availability?The service keeps working when a component fails, by having redundant copies (2 DNS, 2 backends, 2 edges) and automatic or quick failover.
What is a single point of failure?A component whose failure stops the whole service. Ours: the primary nginx edge on Mac 2 (and the Wi-Fi itself).
502 vs 504?502: backend refused the connection (app not running). 504: no answer in time (host off / firewall drop).
Refused vs timed out?Refused: host up, port closed (RST). Timed out: packets dropped or host down.
OSI layers in this project?L7: DNS, HTTP · L6: TLS · L4: TCP/UDP ports · L3: IP / ping · L2/L1: Wi-Fi.
What is a reverse proxy vs forward proxy?Reverse proxy sits in front of servers (nginx here). Forward proxy sits in front of clients (e.g. a company web proxy).
What is TTL?Seconds a DNS answer may be cached. Ours 30 s.
Why a self-signed certificate?.test is private; no public CA will sign it. We trusted our certificate on every client Mac instead of ignoring errors with -k.
Cloud equivalents?dnsmasq → Route 53 · nginx edge → ALB / load balancer · pf rules → security groups · standby edge + DNS change → DNS failover.
Biggest problem you faced?The macOS application firewall on our managed Macs silently blocked nginx/node/dnsmasq after restarts (timeouts while ping worked). We diagnosed it layer by layer: ping OK, TCP timed out, so a firewall, and fixed it by allowing the apps.
What would you improve?Floating IP (keepalived) for the edge, active health checks, HTTPS to the backends, monitoring/alerts, automated DNS failover.
